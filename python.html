Clase 02

Buenas prácticas (PEP8, docstrings) y manejo básico de errores

Transformar "código que funciona" en código legible, documentado y robusto ante errores — la base de calidad que se exige en toda la materia.

Conceptos clave

  • PEP 8: indentación de 4 espacios, snake_case para variables/funciones, CapWords para clases, imports agrupados al inicio.
  • PEP 257 / docstrings: triple comilla """...""", formato con Args, Returns, Raises; se accede con __doc__ y help().
  • Comentarios efectivos: explican el "por qué" (decisiones, reglas de negocio), no repiten el "qué" del código.
  • Excepciones: modelo try / except / else / finally; raise ... from exc para encadenar y conservar la causa original; excepciones propias heredando de ValueError/Exception.
  • E/S de datos: TXT (open()), CSV (csv.DictReader), JSON (json.load/json.dump); pathlib.Path en vez de strings sueltos.

Ejemplo

def cargar_configuracion(ruta: str) -> dict:
    """Carga configuración desde un archivo JSON.

    Args:
        ruta: Ubicación del archivo.
    Returns:
        Diccionario con la configuración.
    Raises:
        FileNotFoundError: Si la ruta no existe.
    """
    try:
        texto = Path(ruta).read_text(encoding="utf-8")
        return json.loads(texto)
    except FileNotFoundError as exc:
        raise FileNotFoundError(f"No existe: {ruta}") from exc
    except json.JSONDecodeError as exc:
        raise ValueError("El archivo no contiene JSON válido") from exc

Errores típicos

  • Nombres crípticos (cp(x) en vez de calcular_promedio(...)).
  • Comentarios que repiten el código en vez de explicar la decisión.
  • except: vacío o except Exception: pass que oculta bugs reales.
  • No cerrar archivos (olvidar with open(...)) ni fijar encoding="utf-8".

Clase 02.1

Manejo robusto de excepciones con JSON, TXT y CSV

Aplica el manejo de errores específicamente a leer/escribir archivos de datos: archivos faltantes, permisos, codificación, formatos inválidos y columnas ausentes.

Conceptos clave

  • Principios: fallar pronto, ser específico (capturar FileNotFoundError, PermissionError, json.JSONDecodeError, csv.Error, UnicodeDecodeError según el caso), cerrar recursos con with, registrar contexto con logging.exception().
  • Flujo recomendado: comprobar ruta → abrir seguro → parsear formato → validar estructura → convertir tipos → reportar/elevar.
  • Excepción de dominio reutilizable, ej. class DataFileError(Exception), que envuelve errores técnicos con raise ... from exc.
  • Capas de error distintas: lectura (FileNotFoundError, OSError), parseo (JSONDecodeError, csv.Error), validación (ValueError, KeyError), negocio (reglas propias).
  • Pandas como alternativa de alto nivel: pd.read_csv(on_bad_lines="error"), pd.to_numeric(errors="raise").

Ejemplo

def leer_ventas_csv(path: str) -> list[dict]:
    columnas = {"fecha", "producto", "region_ventas", "cantidad_ventas"}
    with Path(path).open("r", encoding="utf-8", newline="") as archivo:
        lector = csv.DictReader(archivo)
        if not lector.fieldnames or not columnas.issubset(lector.fieldnames):
            faltantes = columnas - set(lector.fieldnames or [])
            raise ValueError(f"Columnas faltantes: {faltantes}")
        return list(lector)

Antipatrones a evitar

  • Capturar todo con except Exception sin registrar ni reelevar.
  • Ignorar errores (except: pass o devolver [] como si nada hubiese pasado).
  • No validar columnas del CSV/JSON, asumiendo estructura perfecta.
  • Mensajes ambiguos ("Error" sin ruta, operación ni causa).

Clase 02.2

Bibliotecas de ciencia de datos (repaso integrador)

El "mapa" del stack de Python para ciencia de datos — cuál biblioteca usar según la tarea — y puente hacia NumPy/Pandas y Matplotlib/Seaborn.

Conceptos clave

  • NumPy: ndarray, cálculo vectorizado — np.array(), np.mean(), np.where(), np.reshape().
  • pandas: Series/DataFrame — read_csv(), head(), describe(), groupby(), merge().

  • SciPy complementa NumPy (optimización, álgebra lineal, estadística). scikit-learn: patrón fit() / predict() / score().

Ejemplo

try:

except FileNotFoundError:

Clase 03

NumPy y Pandas: arreglos y datos tabulares

Los dos pilares técnicos del resto de la materia: cálculo vectorizado con NumPy y manipulación de datos tabulares con Pandas.

Conceptos clave

  • ndarray: propiedades ndim, shape, size, dtype; conversión con .astype().
  • Vectorización y broadcasting: operar arreglos enteros sin loops for explícitos.
  • Indexación y máscaras booleanas: x[1:3], x[::2], arr[arr >= 18].
  • Series y DataFrame: pd.Series(...), pd.DataFrame({...}); inspección con head(), info(), describe(), dtypes.
  • loc vs iloc: df.loc[] por etiqueta (incluye ambos extremos), df.iloc[] por posición (excluye el final).
  • Condiciones booleanas combinadas con &/| (nunca and/or).
  • Limpieza: .str.replace(), pd.to_numeric(errors="coerce"), .fillna(), .drop_duplicates().
  • Agrupar/pivotear/combinar: groupby().agg(), pd.pivot_table(), pd.merge(on=..., how=...).
  • np.where() para una regla condicional, np.select() para varias reglas a la vez.

Ejemplo

ventas['precio'] = ventas['precio'].str.replace('$', '', regex=False)
ventas['precio'] = pd.to_numeric(ventas['precio'], errors='coerce')
ventas['precio'] = ventas['precio'].fillna(ventas['precio'].median())

condiciones = [reporte['minutos'] <= 25, reporte['minutos'] <= 40]
reporte['clasificacion'] = np.select(condiciones, ['Rápida', 'Normal'], default='Demorada')

Errores típicos

  • Usar and/or en vez de &/| al combinar condiciones en Pandas.
  • Columna numérica que quedó como object por símbolos o texto mezclado ($ en precios, "dos" en vez de 2) — limpiar antes de pd.to_numeric.
  • Confundir df.loc[0:2] (incluye el 2) con df.iloc[0:2] (excluye la posición 2).

Clase 04

Preparación y movimiento de datos: índices, limpieza y formatos

Indexación avanzada, combinar datasets (concat vs. merge), un proceso de limpieza basado en diagnóstico, y persistencia en CSV/Excel/SQL/JSON. La clase más orientada a "pipeline reproducible".

Conceptos clave

  • concat apila (misma estructura, sin clave común) — merge relaciona (clave común, con cardinalidad 1:1/1:N/N:M). Son operaciones distintas que se confunden seguido.
  • merge: tipos de join inner/left/right/outer; validate="many_to_one"; indicator=True para ver qué coincidió.
  • Diagnóstico de calidad: df.isna().sum(), df.duplicated().sum(), df.nunique(), df.describe(include="all").
  • Nulos: eliminar vs. imputar (mediana robusta, moda para categorías); marcar con una columna bandera df['col_faltante'].
  • Tipos: pd.to_numeric(errors="coerce"), pd.to_datetime(errors="coerce", dayfirst=True), .astype("category").
  • Formatos de E/S: CSV (sep, decimal, parse_dates), Excel (sheet_name=None para todas las hojas), SQL (read_sql_query con parámetros — nunca concatenar), JSON (json_normalize para aplanar estructuras anidadas).
  • index=False al exportar, para no escribir el índice como columna.

Ejemplo

mascara = (ventas["importe_num"] >= 800) & ventas["producto"].isin(["A", "B"])
seleccion = ventas.loc[mascara, ["cliente_id", "producto", "importe_num"]]

ventas_clientes = ventas.merge(clientes, on="cliente_id", how="left",
                                validate="many_to_one", indicator=True)

df["importe_num"] = pd.to_numeric(
    df["importe"].str.replace("$", "", regex=False), errors="coerce"
)

Errores típicos

  • Confundir concat con merge, o alinear por índice con concat(axis=1) cuando los índices no son la misma entidad.
  • No validar la cardinalidad antes de un merge → explosión de filas por relación N:M inesperada.
  • No parametrizar consultas SQL (riesgo de inyección).
  • Olvidar index=False al exportar.

Clase 05

Visualización con Matplotlib

Traducir una pregunta analítica en una visualización correcta (tendencia, comparación, distribución, relación), con la interfaz Figure/Axes. Énfasis en comunicación honesta, no sólo en sintaxis.

Conceptos clave

  • Elección de gráfico según la pregunta: tendencia → líneas; comparación → barras (base en cero); distribución → histograma; relación → dispersión (no prueba causalidad).
  • Anatomía: Figure = lienzo completo, Axes = área de dibujo; fig, ax = plt.subplots(...).
  • Subgráficos múltiples: plt.subplots(n, m, figsize=...), indexado axes[i,j].
  • Ajuste lineal con np.polyfit(x, y, 1) para una recta de tendencia sobre un scatter.
  • Cierre: fig.tight_layout(), plt.show(), fig.savefig(..., dpi=...).

Ejemplo

fig, ax = plt.subplots(figsize=(8, 4))
ax.plot(meses, ventas, marker="o")
ax.set_title("Ventas mensuales"); ax.set_xlabel("Mes"); ax.set_ylabel("Unidades")
fig.tight_layout(); plt.show()

m = np.mean(df['minutos'])
plt.hist(df['minutos'], bins=np.arange(15,55,5), color='teal', edgecolor='white')
plt.axvline(m, color='red', linestyle='--', label=f'Media={m:.1f}')
plt.legend()

Errores frecuentes

  • Eje truncado (no empezar en cero) que exagera diferencias en barras.
  • Título genérico ("Ventas") en vez de uno que comunique el hallazgo.
  • Miles de puntos superpuestos en un scatter sin alpha (transparencia).
  • Confundir correlación con causalidad al interpretar una recta ajustada.

Clase 06

Visualización con Seaborn

Seaborn como interfaz estadística de alto nivel sobre Matplotlib, usada junto con Pandas: Pandas organiza → Seaborn visualiza → Matplotlib controla figura/exportación.

Conceptos clave

  • sns.heatmap(df.corr(), annot=True): cerca de +1/-1 = asociación lineal fuerte; cerca de 0 = poca asociación lineal (no independencia).
  • sns.boxplot() + sns.stripplot(): mediana, caja = rango intercuartílico, puntos externos = posibles atípicos.
  • sns.pairplot(hue=...): matriz de relaciones por pares — útil con pocas variables, lento con muchas.
  • Multivariado con un solo scatter: hue, size, style — una variable por canal visual, sin sobrecargar.
  • Exportación para informes: PNG (dpi=300) para web/Office, PDF/SVG (vectorial) para impresión.

Ejemplo

corr = df.select_dtypes("number").corr()
sns.heatmap(corr, annot=True, cmap="vlag", vmin=-1, vmax=1)

sns.boxplot(data=df, x="Curso", y="Nota", hue="Curso", legend=False)
sns.stripplot(data=df, x="Curso", y="Nota", color="black", alpha=.4)

sns.scatterplot(data=df, x="Horas", y="Nota", hue="Curso", size="Proyectos",
                 style="Curso", sizes=(40, 220), alpha=.78)

Errores típicos

  • Interpretar correlación ≈ 0 como "independencia" (sólo indica poca asociación lineal).
  • Confundir correlación con causalidad al leer un heatmap o regplot.
  • pairplot con demasiadas columnas: lento y difícil de leer.
  • Codificar más de una variable por canal visual sin criterio (color + forma + tamaño a la vez).

Guía del 2.º parcial · 1 de 3

pandas aplicado: encontrar y corregir errores

El 2.º parcial pide resolver ejercicios de código con errores: leés el código, encontrás qué falla y lo dejás andando, explicando el diagnóstico. Esta sección junta los conceptos de pandas que esos ejercicios usan: describe, pivot_table, cuartiles e IQR, valores faltantes, pd.cut y groupby.apply.

Fuente: el simulacro A del 2.º parcial que dio la cátedra y su resolución explicada (hecha con Claude), no las diapositivas. Todo el código de acá se ejecutó y las salidas son reales. Cuando lleguen los materiales con los números de clase, se contrasta y se reubica.

Cómo encarar un «código con errores»

  • Leé el objetivo antes que el código: ¿qué tendría que producir?
  • Revisá línea por línea: nombres de columnas (¿coinciden con los del DataFrame?), nombres de métodos y parámetros (¿están bien escritos? ¿en plural?), paréntesis y la fórmula (¿la cuenta es la correcta?).
  • Distinguí dos tipos de error. Los que rompen el programa (da un error y frena) y los lógicos (corre, pero el resultado está mal: una fórmula equivocada). Los segundos son más peligrosos porque no avisan.
  • En el espacio de diagnóstico escribí qué falla, por qué y cómo se corrige, con el resultado esperado.

Tres ideas que se repiten en todos los ejercicios

  • Un método se ejecuta con paréntesis. df["x"].mean no calcula nada: devuelve el método en sí (<bound method …>) y, si lo usás en una cuenta, da TypeError.
  • Los parámetros se escriben exactamente como pandas los espera: columns, no column; values, no value; include_groups, no include_group. Un parámetro mal escrito da TypeError: unexpected keyword argument.
  • Los nombres de columnas se copian tal cual: "ciudades" en vez de "ciudad" da KeyError. Y salvo el primer argumento, conviene pasar todo con nombre: un valor posicional puede caer en el parámetro equivocado sin que haya error.

Estadística descriptiva: describe, media, mediana y desvío

describe() resume de una vez las columnas numéricas: count (datos no vacíos), mean (media), std (desvío estándar), min/max y los cuartiles 25%, 50% (la mediana) y 75%. Sobre una sola columna (una Series) también existe.

import pandas as pd

df = pd.DataFrame({"edad": [34, 45, 52, 41, 63],
                   "presion_sistolica": [118, 132, 145, 128, 151]})

print(df["presion_sistolica"].describe())          # describe(), sin «s», de UNA columna
print("Mediana:", df["presion_sistolica"].median()) # median() con paréntesis
# count 5 · mean 134.8 · std 13.255 · min 118 · 25% 128 · 50% 132 · 75% 145 · max 151
  • Media (134,8): suma de todos / cantidad. Usa todos los valores, así que un extremo la «arrastra».
  • Mediana (132): el valor central de los datos ordenados. Solo depende de la posición, así que es robusta a outliers: si el 151 fuera 300, la media subiría a 164,6 y la mediana seguiría en 132.
  • Desvío estándar (≈ 13,3): cuánto se alejan, en promedio, los datos de la media. Chico = datos parecidos; grande = muy dispersos. pandas calcula el desvío muestral (divide por n − 1).

Tablas dinámicas con pivot_table

Reorganiza una tabla «larga» en una tabla «cruzada». Le decís cuatro cosas:

index¿Qué va en las filas?
columns¿Qué va en las columnas?
values¿Qué número va adentro de las celdas?
aggfuncSi hay varios datos para una celda, ¿cómo los resumo? "mean", "sum", "count", "min", "max", "median". No existe "average": el promedio es "mean".
margins=TrueAgrega una fila y una columna All con el resumen general (se renombra con margins_name="Total").
df = pd.DataFrame({"ciudad": ["A", "A", "B", "B"],
                   "estacion": ["Verano", "Invierno", "Verano", "Invierno"],
                   "temperatura": [29, 14, 31, 12]})

tabla = pd.pivot_table(df, index="ciudad", columns="estacion",
                       values="temperatura", aggfunc="mean", margins=True)
# estacion  Invierno  Verano   All
# A             14.0    29.0  21.5
# B             12.0    31.0  21.5
# All           13.0    30.0  21.5

Se lee así: fila A × columna Verano = 29 (hay un solo dato). La columna All de la fila A es el promedio anual de A: (14 + 29) / 2 = 21,5. La esquina All/All es el promedio de los cuatro datos.

Cuartiles, IQR y valores atípicos

  • Cuartiles: parten los datos ordenados en 4 partes. Q1 (percentil 25), Q2 = mediana, Q3 (percentil 75).
  • IQR (rango intercuartílico) = Q3 − Q1. Es una resta, no una suma.
  • Regla de Tukey: es atípico lo que cae fuera de Q1 − 1,5·IQR y Q3 + 1,5·IQR. Es la misma regla con que el boxplot dibuja los puntos sueltos.
  • quantile() recibe una proporción entre 0 y 1 (0.25), no un porcentaje: quantile(25) da ValueError.
pm25 = pd.Series([12, 14, 13, 15, 16, 14, 80])      # µg/m³
q1 = pm25.quantile(0.25)        # 13.5
q3 = pm25.quantile(0.75)        # 15.5
iqr = q3 - q1                   # 2.0
limite_superior = q3 + 1.5 * iqr    # 18.5
limite_inferior = q1 - 1.5 * iqr    # 10.5

# | = «o» y cada condición entre paréntesis (con Series no sirve «and»/«or»)
atipicos = pm25[(pm25 > limite_superior) | (pm25 < limite_inferior)]   # el 80 (índice 6)

pandas interpola linealmente para los cuartiles (por eso aparece 13,5): otros métodos manuales pueden dar valores levemente distintos, pero la conclusión es la misma. Y un atípico no se borra automáticamente: primero se revisa si es un error de carga o un evento real.

Valores faltantes en una tabla dinámica

  • Un dato faltante (None) se guarda como NaN: «no tengo el dato». No es lo mismo que cero: que no se midió la emisión de Energía en 2023 no significa que haya emitido 0.
  • fill_value reemplaza las celdas vacías del resultado y debe ser un número (0), no un texto ("0"). Pero rellenar con 0 falsea la tabla: es una decisión que hay que justificar.
  • Trampa: con aggfunc="sum" una celda que solo tenía NaN aparece como 0 (la suma de nada es 0). Para conservar el NaN se usa sum(min_count=1): «sumá solo si hay al menos un dato real».
df = pd.DataFrame({"anio": [2022, 2022, 2023, 2023],
                   "sector": ["Energía", "Transporte", "Energía", "Transporte"],
                   "co2": [120.0, 80.0, None, 85.0]})

tabla = df.pivot_table(index="sector", columns="anio", values="co2",
                       aggfunc=lambda s: s.sum(min_count=1))       # conserva el NaN
tabla["Total"] = tabla.sum(axis=1, min_count=1)      # axis=1: a lo largo de cada fila
# anio         2022  2023  Total
# Energía     120.0   NaN  120.0       (el total de Energía solo cuenta 2022)
# Transporte   80.0  85.0  165.0

Si en cambio se decide (y se justifica) tratar el faltante como 0, los totales salen con aggfunc="sum", fill_value=0, margins=True, margins_name="Total".

Variables derivadas y pd.cut

  • Variable derivada: una columna nueva calculada de otras, df["imc"] = …. pandas hace la cuenta fila por fila.
  • Orden de las operaciones: ** (potencia) se resuelve antes que * y /. IMC = peso / altura²: peso / altura ** 2. peso / altura * 2 es (peso / altura) * 2: un error lógico, no avisa.
  • Discretizar = pasar un número a categorías con pd.cut(x, bins=…, labels=…). bins son los bordes y labels los nombres: cantidad de labels = cantidad de bordes − 1 (5 bordes forman 4 intervalos).
  • Pasá los argumentos con nombre. El tercer argumento posicional de pd.cut es right, no labels: pd.cut(imc, bins, labels) no da error, pero devuelve intervalos en vez de nombres.
  • right=True (por defecto) incluye el borde derecho: (a, b]. Con right=False son [a, b), y un IMC de 25,0 cae en «Sobrepeso», como en la tabla de la OMS.
df = pd.DataFrame({"peso_kg": [60, 78, 95, 52], "altura_m": [1.65, 1.75, 1.70, 1.60]})
df["imc"] = (df["peso_kg"] / df["altura_m"] ** 2).round(1)      # 22.0, 25.5, 32.9, 20.3

bins = [0, 18.5, 25, 30, 100]                          # 5 bordes → 4 intervalos
labels = ["Bajo", "Normal", "Sobrepeso", "Obesidad"]   # 4 etiquetas
df["categoria"] = pd.cut(df["imc"], bins=bins, labels=labels, right=False)
# Normal, Sobrepeso, Obesidad, Normal

groupby + apply: promedio ponderado y división por cero

  • Promedio ponderado = Σ(valor × peso) / Σ(peso). Norte: (12000·2 + 18000·1) / 3 = 14000 (el simple daría 15000: la zona con más gente pesa más).
  • groupby("region").apply(f): divide el DataFrame en grupos, aplica f a cada mini-DataFrame y combina los resultados. include_groups=False (plural, desde pandas 2.2) evita pasarle a f la columna por la que se agrupó.
  • División por cero: si los pesos de un grupo suman 0, no hay promedio posible. La función «segura» chequea antes y devuelve np.nan (no 0). Con np.average la división por cero corta con ZeroDivisionError.
  • Si la función devuelve una pd.Series con etiquetas, cada etiqueta se vuelve una columna: así el resultado es un DataFrame con varias columnas por grupo.
import numpy as np

def promedio_ponderado(g):                       # g = mini-DataFrame de UNA región
    poblacion_total = g["poblacion"].sum()       # sum() con paréntesis
    if poblacion_total == 0:
        pib = np.nan                             # no se puede ponderar
    else:
        pib = (g["pib_pc"] * g["poblacion"]).sum() / poblacion_total
    return pd.Series({"pib_ponderado": pib, "poblacion_total": poblacion_total})

resultado = df.groupby("region").apply(promedio_ponderado, include_groups=False)
#         pib_ponderado  poblacion_total
# Norte         14000.0              3.0
# Sur           15000.0              3.0

Además, el cuerpo de una función def va indentado (4 espacios): sin sangría da IndentationError.

Errores típicos de un vistazo

  • Método sin paréntesis: .mean, .sum → .median(), .sum().
  • Nombre de método mal escrito: describes() → describe() (AttributeError).
  • Nombre de columna distinto al real: "ciudades" → "ciudad" (KeyError).
  • Parámetro en singular: column=, value=, include_group= → plural (TypeError).
  • aggfunc inexistente: "average" → "mean".
  • Percentil como porcentaje: quantile(25) → quantile(0.25) (ValueError).
  • Fórmula equivocada: q1 + q3 → q3 - q1; altura * 2 → altura ** 2 (error lógico).
  • Tipo de dato equivocado: fill_value="0" → fill_value=0.
  • Faltante tratado como cero: sum sobre un grupo vacío → sum(min_count=1) y justificar la decisión.
  • Labels ≠ intervalos: 5 labels con 5 bordes → 4 labels; y pasarlos con nombre.
  • División por cero: suma / pesos → if pesos == 0: np.nan.
  • Y/o con Series: and/or → &/| con cada condición entre paréntesis.

Git y trabajo en equipo con datos

Git registra los cambios de un proyecto de análisis de datos y permite que varias personas trabajen en paralelo sin pisarse. Acá están el vocabulario, los comandos, qué no versionar, cómo trabajar con ramas y cómo resolver los problemas típicos (conflictos en notebooks, datos grandes y sensibles).

Fuente: simulacro A del 2.º parcial de la cátedra y su resolución (hecha con Claude); no son las diapositivas.

Qué es Git y vocabulario mínimo

  • Git es un sistema de control de versiones: guarda la historia de los cambios, permite volver a un punto anterior y ver qué cambió, quién y por qué. Pensalo como un «guardar partida».
  • GitHub / GitLab no son Git: son sitios donde se aloja una copia del repositorio (el remoto) para compartirlo y revisarlo. Git funciona perfectamente sin ellos.
  • Repositorio: la carpeta del proyecto más toda su historia (en la carpeta oculta .git). Commit: una «foto» guardada del proyecto, con un mensaje. Staging: la «sala de espera» de los cambios que entrarán en el próximo commit.
  • Rama (branch): una línea de trabajo paralela, para probar sin tocar main. Merge: unir los cambios de una rama en otra. Conflicto: dos ramas cambiaron las mismas líneas y Git te pide que decidas. Pull request (PR): pedido para fusionar una rama donde un compañero revisa antes.

El flujo básico: tres lugares

carpeta de trabajo   (editás archivos)
      │  git add
      ▼
staging              (cambios preparados)
      │  git commit -m "..."
      ▼
historial del repo   (cambios guardados)
      │  git push
      ▼
remoto (GitHub)      (cambios compartidos)
git initConvierte la carpeta actual en repositorio (una sola vez; crea .git).
git statusMuestra qué archivos cambiaron y cuáles están preparados.
git add archivoPasa los cambios de ese archivo al staging.
git commit -m "mensaje"Guarda lo que está en staging como un commit. El mensaje, en presente y diciendo qué hace el cambio («Agrega limpieza de valores faltantes»).
git logMuestra el historial de commits.
git push / git pullSube tus commits al remoto / trae los del remoto.
git switch -c nombreCrea una rama nueva y se pasa a ella.

Interpretar git status: si un archivo aparece como modified pero no bajo «Changes to be committed», el cambio está en la carpeta de trabajo y no en el staging. Falta git add src/limpieza.py; recién ahí el commit lo incluye.

Qué no se versiona: .gitignore

.gitignore lista lo que Git debe ignorar. En un proyecto de datos normalmente: secretos y configuración local (.env), el entorno virtual (.venv/), caché (__pycache__/), los datos (data/) y salidas generadas. El README, el código (src/) y los tests sí se versionan. Nunca se suben contraseñas: todo lo que entra a Git queda en el historial, y lo ve cualquiera con acceso.

# .gitignore
.env
.venv/
__pycache__/
data/
*.csv

Estrategia de ramas para un equipo

  • main protegida: nadie hace push directo; solo entra código por pull request aprobado. Siempre debe funcionar.
  • Una rama por tarea, con nombres claros: feature/ingestion, feature/limpieza, feature/modelado.
  • Pull requests con revisión: otro integrante revisa el código y, idealmente, corren tests automáticos (CI, por ejemplo GitHub Actions). Se fusiona solo si se aprueba y los tests pasan.
  • Ramas cortas y fusiones frecuentes: cuanto más vive una rama separada, más conflictos. Traer seguido los cambios de main (git pull origin main o rebase) para resolverlos de a poco.
  • Separar responsabilidades en módulos (ingestion.py, limpieza.py, modelado.py) para que no se editen los mismos archivos. Opcional: una rama develop de integración (Git Flow); para equipos chicos alcanza con main + ramas de tarea.

Conflictos en un notebook

Un notebook (.ipynb) por dentro es un archivo JSON enorme (código, salidas, imágenes, metadatos): las marcas de conflicto (<<<<<<<, =======, >>>>>>>) pueden romperlo y hacer que no abra. Procedimiento seguro:

  1. No resolver a ciegas ni borrar una versión entera. Primero respaldar las dos (por ejemplo git show main:analisis.ipynb > analisis_main.ipynb) o trabajar en una rama aparte.
  2. Comparar con una herramienta que entienda notebooks: nbdime (nbdiff, nbmerge) o el diff de Jupyter/VS Code, que muestran las diferencias por celda.
  3. Hablar con la otra persona y decidir qué celdas quedan; si los dos análisis sirven, conservarlos en celdas separadas.
  4. Reejecutar de cero (Restart & Run All) para verificar que funciona y que los resultados son coherentes.
  5. Recién ahí git add y git commit marcando que se resolvió el conflicto.

Para prevenirlos: mover la lógica a archivos .py, que cada persona trabaje en notebooks distintos y limpiar las salidas antes de commitear (por ejemplo con nbstripout).

Datos grandes y sensibles

Un CSV de 4 GB con datos personales no debería subirse a Git:

  • Tamaño: Git está pensado para texto chico. GitHub rechaza archivos de más de 100 MB y cada versión del CSV queda para siempre en el historial: el repo se vuelve enorme y lento de clonar.
  • Privacidad: cualquiera con acceso al repo vería los datos, y aunque los borres después, siguen en el historial. Además puede violar normas de protección de datos (en Argentina, la Ley 25.326).
  • Git no maneja permisos finos, cifrado ni auditoría de quién accede.

Estrategia reproducible: data/ en .gitignore; el archivo en un almacenamiento seguro con control de acceso (servidor, bucket con permisos, base de datos), idealmente cifrado; versionar la referencia al dato, no el dato (con DVC se sube a Git un archivo chico que apunta a la versión exacta, o al menos un script descargar_datos.py con un checksum); documentar en el README de dónde se obtiene y cómo se coloca en data/raw/; usar una muestra anonimizada o sintética para desarrollo; y las credenciales en .env (ignorado), nunca en el código. Git LFS sirve para archivos grandes pero no resuelve el problema de los datos personales.

Entornos, reproducibilidad y estructura de proyectos

Que otra persona (o vos en seis meses) pueda correr el proyecto y obtener los mismos resultados. Es el hilo conductor de casi todas las preguntas: entorno virtual, dependencias versionadas, notebook corrido de cero y lógica reutilizable en módulos con tests.

Fuente: simulacro A del 2.º parcial de la cátedra y su resolución (hecha con Claude); no son las diapositivas. El tema de testing acá es introductorio; se amplía cuando lleguen los materiales de la cátedra.

Entornos virtuales y dependencias

  • Un entorno virtual (.venv) es una instalación de Python aislada por proyecto, con sus propias librerías y versiones: un proyecto que necesita pandas 2.1 no choca con otro que necesita pandas 3.0.
  • Las dependencias (qué librerías y qué versiones) se anotan en requirements.txt o pyproject.toml. Ese archivo sí se sube a Git; la carpeta .venv no (es pesada y depende de cada computadora: cada uno la recrea).
  • Lo que mejora la reproducibilidad: documentar la versión de Python y versionar el archivo de dependencias. No sirve enviar __pycache__ (archivos compilados temporales), subir .venv ni borrar las importaciones.
python -m venv .venv                  # crear el entorno
source .venv/bin/activate             # activarlo (Windows: .venv\Scripts\activate)
pip install -r requirements.txt       # instalar las dependencias anotadas

Secuencia correcta de trabajo

  1. Activar el entorno virtual: así todo lo que sigue ocurre en el entorno del proyecto.
  2. Instalar las dependencias (pip install -r requirements.txt): si instalás antes de activar, se instalan en el lugar equivocado.
  3. Ejecutar el notebook desde el inicio (Restart Kernel & Run All): no dependés de celdas corridas a mano en otro orden ni de variables que quedaron en memoria.
  4. Verificar los resultados: que coincidan con lo esperado o con los tests.

Separar los notebooks de la lógica reutilizable (principio DRY)

Si el mismo bloque de limpieza está copiado en cuatro notebooks y encontrás un error, hay que arreglarlo cuatro veces (y te vas a olvidar alguna): viola DRY (Don't Repeat Yourself). La solución: una función en un módulo, importarla desde los notebooks y escribir tests.

# src/proyecto/limpieza.py
def limpiar_datos(df):
    """Elimina duplicados y normaliza los nombres de las columnas."""
    df = df.drop_duplicates()
    df.columns = df.columns.str.lower().str.strip()
    return df

# en cada notebook (en vez de copiar el bloque):
from proyecto.limpieza import limpiar_datos

# tests/test_limpieza.py   (se corren con:  pytest)
import pandas as pd
from proyecto.limpieza import limpiar_datos

def test_limpiar_datos_quita_duplicados_y_normaliza_columnas():
    df = pd.DataFrame({" Edad ": [30, 30, 41], "CIUDAD": ["A", "A", "B"]})
    limpio = limpiar_datos(df)
    assert list(limpio.columns) == ["edad", "ciudad"]
    assert len(limpio) == 2
  • Para que from proyecto.limpieza import … funcione desde un notebook, el proyecto tiene que estar instalado en el entorno: con un pyproject.toml, pip install -e . (modo editable).
  • Un test llama a tu función con un ejemplo y verifica el resultado con assert. Sirve para saber que sigue funcionando cuando la cambiás. Los notebooks quedan para explorar y mostrar.
